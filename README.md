# Remnawave Self-Steal Nginx

**Версия в разработке. Перед использованием на рабочей VPS необходимо
проверить установку и работу на тестовом сервере с Ubuntu 24.04.**

Установщик создаёт HTTP-сайт для подтверждения домена Let's Encrypt
и локальный TLS-сервер nginx на `127.0.0.1:9443` с поддержкой HTTP/2
и TLS 1.3. Настройки Remnawave Node вносятся вручную через панель.
Скрипт не изменяет Docker, Remnawave, Xray и правила сетевого экрана.

## Требования к серверу

- Ubuntu 24.04 LTS, архитектура x86_64, запуск от root.
- Домен с одной A-записью на публичный IPv4 этой VPS, без AAAA-записи.
- Свободные TCP/80 и TCP/9443 перед первой установкой.
- Отсутствие ранее установленного nginx. Стандартный сайт из пакета nginx
  после установки сохраняется.
- Отсутствие ранее созданного сертификата Let's Encrypt для выбранного домена
  при первой установке. При повторном запуске свой сертификат используется повторно.
- Для установленного Remnawave Node — режим Docker `network_mode: host`.
- Доступные `curl` с HTTP/2, `resolvectl` и `ss` для предварительной проверки.
  Пакет curl из Ubuntu поддерживает HTTP/2.

При объёме RAM меньше 1 ГиБ или отсутствии swap выводится предупреждение.
Если свободного места на разделе `/` меньше 2 ГиБ, установка прекращается;
при остатке от 2 до 4 ГиБ выводится предупреждение. Установщик не выполняет
полное обновление системы и не перезагружает VPS.

## Установка с нуля: есть панель и пустая VPS

Эта инструкция рассчитана на готовую панель Remnawave и **отдельную пустую VPS
для ноды**. Потребуются доступ администратора к панели, SSH-доступ к VPS,
публичный IPv4 сервера и собственный домен с доступом к управлению DNS.
Если домена ещё нет, сначала зарегистрируй его. Домен панели можно сохранить:
для ноды создай отдельный поддомен, например `node.example.com`.
Не перенаправляй существующую DNS-запись панели на новую VPS.

Панель управляет пользователями и настройками, Node обслуживает VPN-подключения,
а этот проект подготавливает локальный сайт nginx для REALITY.
Последовательность: **Node → DNS → self-steal → профиль → привязка ноды →
Host → группа доступа → пользователь → клиент**.

Команды с пометкой «на VPS ноды» выполняй по SSH именно на новой VPS.
Настройки с пометкой «в панели» меняй в веб-интерфейсе Remnawave.
Значения ниже — примеры: подставляй свой домен, IP и порты.

| Значение | Назначение |
| --- | --- |
| `node.example.com` | Поддомен для self-steal и подключения клиентов |
| `203.0.113.10` | Пример IPv4; обязательно замени реальным адресом VPS ноды |
| `2222` | Пример `NODE_PORT`: API ноды для связи с панелью |
| `8443` | Публичный порт VPN из примера профиля ниже; в схеме с двумя inbound на нём может работать XHTTP |
| `127.0.0.1:9443` | Локальный TLS-сервер nginx, доступный Xray на этой VPS |
| `Self-Steal` | Имя отдельного Config Profile в примере |
| `VLESS_SELFSTEAL` | `tag` входящего подключения (inbound) в примере |

### 1. Установи Remnawave Node и подключи к панели

На VPS ноды установи Docker и Node по
[официальной инструкции Remnawave Node](https://docs.rw/install/remnawave-node/).
В панели открой **Nodes → Management**, начни создание ноды и укажи её реальный
IP. Скопируй предоставленный панелью `docker-compose.yml` в каталог Node
на этой VPS и запусти его по инструкции. Используй выданные панелью секреты.

В конфигурации сервиса Node нужен `network_mode: host`: тогда Xray видит
nginx по адресу `127.0.0.1:9443` на той же VPS. `NODE_PORT` в Compose
и порт в карточке ноды должны совпадать. Это API-порт, а не порт VPN.
Разреши доступ к нему только с IP сервера панели; сохрани свой доступ по SSH.

Для завершения создания ноды можно выбрать имеющийся штатный Config Profile,
не занимающий TCP/80 и TCP/9443. Профиль для self steal создадим после nginx.
Дождись связи панели с нодой. Если связи нет, исправь её по документации
до продолжения. Наличие ноды в списке само по себе ещё не означает готовый VPN.

### 2. Создай A-запись и настрой доступ к портам

В DNS-панели, обслуживающей домен `example.com`, создай запись:

| Поле DNS | Значение для примера |
| --- | --- |
| Тип | `A` |
| Имя / Host | `node` — обычно только поддомен; некоторые панели требуют `node.example.com` |
| Значение / IPv4 | Реальный публичный IPv4 **VPS ноды**, не сервера панели |
| TTL | Автоматический или стандартный |
| Проксирование Cloudflare | Выключено: **DNS only** |

В результате полное имя `node.example.com` должно указывать только на VPS ноды.
Для **этого имени** не должно быть AAAA-записи, CNAME или дополнительных A-записей
с другими адресами. Записи остальных поддоменов, включая панель, не удаляй.
Дождись распространения DNS: обновление не всегда происходит сразу.

Настрой входящие соединения и в сетевом экране VPS, и в правилах хостинга:

| Порт | Кому нужен доступ |
| --- | --- |
| Твой SSH-порт | Тебе для управления сервером |
| TCP/`NODE_PORT`, например 2222 | Только серверу панели |
| TCP/80 | Из интернета: выпуск и дальнейшее продление сертификата |
| TCP/8443 | Из интернета: VPN-клиенты для профиля из этой инструкции или XHTTP inbound |
| TCP/443 | Из интернета, если добавлен отдельный TCP/REALITY inbound на этом порту |
| TCP/9443 | Только локально; наружу не открывай |

Если выбираешь другой публичный VPN-порт, используй его одинаково в профиле,
Hosts и сетевых правилах. TCP/443 для базового примера с одним inbound не требуется.
Для схемы с TCP/443 и XHTTP/8443 открой оба публичных порта.
Серверу также нужен исходящий доступ к DNS, репозиториям Ubuntu и HTTPS-сервисам
GitHub, Let's Encrypt и `api.ipify.org`. Не включай сетевой экран с пустыми
правилами: сначала сохрани разрешение для текущего SSH-подключения.

### 3. Скачай self-steal на VPS ноды

Не устанавливай nginx или Certbot вручную перед этим шагом: ими займётся
установщик. Открой SSH-сессию на VPS ноды и установи необходимые инструменты:

```bash
sudo -i
apt-get update
apt-get install -y --no-install-recommends git curl ca-certificates openssl iproute2 python3-configobj
```

Если уже вошёл как root, `sudo -i` пропусти. Отправлять коммит через `git push`
для установки не требуется: дальше скачивается опубликованная версия проекта.

Склонируй репозиторий:

```bash
git clone https://github.com/Inch1337/Remnawave-Selfsteal-Nginx.git /opt/remnawave-selfsteal
cd /opt/remnawave-selfsteal
git log -1 --oneline
```

Если он уже склонирован и в нём нет несохранённых правок:

```bash
cd /opt/remnawave-selfsteal
git pull --ff-only
git log -1 --oneline
```

Убедись, что показан нужный коммит. Файлы `install.sh`, `check.sh` и
`uninstall.sh` должны оставаться в одной папке. Отдельный старый
`/root/install.sh` не обновляется при клонировании — запускай скрипты
именно из `/opt/remnawave-selfsteal`.

### 4. Выполни предварительную проверку VPS

На VPS ноды из каталога `/opt/remnawave-selfsteal`:

```bash
bash install.sh --check
```

```bash
bash -n install.sh &&
bash -n check.sh &&
bash -n uninstall.sh &&
bash -n tests/test_helpers.sh &&

```

Ожидается `Helper checks passed.` Эти проверки не устанавливают nginx и

Введи свой домен, например `node.example.com`. Ожидается сообщение об
успешной предварительной проверке. Этот режим не меняет систему. Если отсутствует
`resolvectl`, сначала выясни, как настроен DNS на VPS; не заменяй работающую
настройку DNS вслепую.

**Пока не меняй target, SNI и Hosts в Remnawave:** нового TLS-сервера
на этом этапе ещё нет.

### 5. Установи и проверь self-steal

```bash
set -o pipefail
bash install.sh --install 2>&1 | tee install.log
```

Введи тот же домен и контактный email для Let's Encrypt. Установщик
подготовит nginx, получит сертификат и выполнит пробное продление. После этого
он отдельно запустит скрипт применения сертификата (deploy hook), проверит
его код завершения и доступность nginx. Дождись `Installation complete.` Затем:

```bash
bash check.sh 2>&1 | tee check.log
```

Продолжай только после `[OK]` у всех пунктов и `SELF-STEAL READY`.
Теперь на VPS подготовлен локальный nginx для self-steal; подключение
через сам Remnawave проверяется после следующих шагов.

### 6. Создай или измени Config Profile в панели

**Меняется JSON в веб-панели: Config Profiles → нужный профиль → редактор.**
В нём настройки self-steal находятся по пути
`inbounds[] → нужный inbound → streamSettings → realitySettings`.
Это не `docker-compose.yml`, не `.env` панели и не конфиг nginx.

#### Если VPN настраивается впервые

После успешной установки self-steal подготовь ключ REALITY и Short ID.
На VPS ноды выполни:

```bash
docker exec remnanode xray x25519
openssl rand -hex 8
```

`remnanode` — имя контейнера из твоего Compose; если оно другое, подставь своё.
В образе с другим именем исполняемого файла Xray используй путь ядра из журнала
запуска Node (например, `rw-core` вместо `xray`). Не устанавливай второе ядро
на хост только ради генерации ключей.

Из вывода первой команды возьми **PrivateKey / Private key** для `privateKey`.
Результат второй команды — 16 шестнадцатеричных символов для `shortIds`.
Приватный ключ не публикуй и не вставляй в клиент. Не используй здесь `SECRET_KEY`
из Compose или ключ сертификата nginx: это разные ключи.
Правила параметров описаны в [документации REALITY](https://xtls.github.io/en/config/transports/reality.html).

В панели открой **Config Profiles → Create Config Profile**, назови профиль
`Self-Steal`. Для **нового отдельного профиля** используй этот базовый пример
VLESS + RAW/TCP + REALITY, заменив три значения перед сохранением:

```json
{
  "log": {
    "loglevel": "warning"
  },
  "inbounds": [
    {
      "tag": "VLESS_SELFSTEAL",
      "listen": "0.0.0.0",
      "port": 8443,
      "protocol": "vless",
      "settings": {
        "clients": [],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "raw",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "target": "127.0.0.1:9443",
          "xver": 0,
          "serverNames": ["node.example.com"],
          "privateKey": "REPLACE_WITH_PRIVATE_KEY",
          "shortIds": ["REPLACE_WITH_SHORT_ID"]
        }
      }
    }
  ],
  "outbounds": [
    {
      "tag": "DIRECT",
      "protocol": "freedom"
    }
  ]
}
```

Замени `node.example.com` своим доменом из установщика, `REPLACE_WITH_PRIVATE_KEY`
приватным ключом REALITY, а `REPLACE_WITH_SHORT_ID` — полученным Short ID.
Если выбран другой порт, замени и `8443`. Маркеры `REPLACE_WITH_...` оставлять нельзя.
Пустой `clients` оставь: пользователей добавляет Remnawave через панель.
Пример рассчитан на одну ноду и прямой выход в интернет, без дополнительных
правил маршрутизации. Он не должен заменять рабочий профиль с другими inbound.
Использование `clients: []` и RAW/REALITY показано также в
[примерах конфигурации Remnawave](https://docs.rw/learn-en/server-routing/).

#### Если VLESS/REALITY уже настроен

Сохрани прежние значения профиля и карточки Host, чтобы можно было вернуть
рабочее подключение. Если профиль общий для нескольких нод с разными
доменами, создай отдельную копию для этой ноды и назначь ей нужный inbound.
Для работающего профиля новые ключи генерировать не нужно.

В панели открой **Config Profiles**, выбери профиль нужной ноды и её
REALITY inbound. В `streamSettings.realitySettings` измени только эти поля:

```json
{
  "target": "127.0.0.1:9443",
  "serverNames": ["node.example.com"],
  "xver": 0
}
```

Это фрагмент настроек, а не полный профиль. Подставь домен, использованный
при установке. Сохрани остальные параметры REALITY, включая `privateKey`
и `shortIds`, а также существующие параметры протокола и транспорта.
В конфигурации, использующей старое имя `dest`, замени соответствующий
target-параметр, не оставляя противоречащие друг другу `dest` и `target`.

Публичный `port` inbound оставь прежним — например, `8443`. Значение
`9443` здесь используется только внутри `target`. `xver: 0` соответствует
созданному nginx без PROXY protocol.

Сохрани профиль. Если существующий inbound использует другой протокол или
транспорт, три поля выше не превращают его в VLESS/REALITY: создай отдельный
профиль по примеру для первой установки.

#### Если на ноде есть TCP и XHTTP REALITY одновременно

Оставь оба inbound в рабочем Config Profile. Каждый из них должен иметь свой
публичный порт, например TCP/443 и XHTTP/8443. В **каждом**
`streamSettings.realitySettings` укажи `target: "127.0.0.1:9443"` и `xver: 0`.
Для одного домена self-steal впиши домен сертификата nginx в `serverNames`
каждого inbound и в SNI соответствующего Host. У XHTTP сохрани
`network: "xhttp"` и его `xhttpSettings`, например `mode: "auto"` и
`path: "/"`; этот путь должен совпадать с настройкой клиента. Не меняй
`privateKey`, `shortIds`, настройки DNS, маршрутизации и уже работающие
публичные порты только ради self-steal. Один локальный nginx на
`127.0.0.1:9443` может обслуживать маскировку обоих inbound; второй nginx
или отдельный сертификат для того же домена не нужен.

Если у TCP inbound в `serverNames` используется **другой** домен, его нельзя
без изменений направлять на локальный сайт с сертификатом `node.example.com`.
Для этого установщика приведи SNI/`serverNames` обоих inbound к домену
выданного сертификата. Иной домен требует отдельно настроенного TLS-сайта;
этот скрипт его не создаёт. Поля с закрытым ключом и Short ID держи в
секрете. Весь Xray JSON профиля установщик не читает и не меняет — после
сохранения профиля проверь его применение в панели.

### 7. Назначь профиль и включи inbound на ноде

В панели открой **Nodes → Management → карточка нужной ноды → Change Profile**
(или раздел выбора Config Profile в карточке). Выбери `Self-Steal` и включи
inbound `VLESS_SELFSTEAL`. Для своего существующего профиля выбери его имя
и соответствующий REALITY inbound. Примени изменения и дождись запуска Xray
без ошибок. Подробнее — в [инструкции Config Profiles](https://docs.rw/learn-en/config-profiles/).

Если профиль сохранён, но не назначен ноде, или inbound не включён,
его публичный порт не начнёт обслуживать клиентов. Ручное редактирование
генерируемого Xray-конфига в контейнере не заменяет этот шаг.
При двух inbound включи на ноде оба, если хочешь выдавать оба варианта
подключения.
Сертификат Let's Encrypt остаётся у nginx на VPS: для этой схемы REALITY
переносить его в панель или добавлять в `tlsSettings` ноды не требуется.

### 8. Создай Host и укажи SNI в панели

Открой **Hosts → Create new host**. Если карточка для этой ноды уже есть,
отредактируй её. Укажи понятное название, например `Мой VPN`, и включи
доступность Host для пользователей (Host visibility).

| Поле | Что указать |
| --- | --- |
| Inbound | `Self-Steal → VLESS_SELFSTEAL` либо твой REALITY inbound, включённый на ноде |
| Address | `node.example.com` либо публичный IP этой VPS; подходящий существующий адрес можно сохранить |
| Port | Публичный порт inbound, например `8443` |
| Advanced Options → SNI | `node.example.com` — тот же домен, что в сертификате и `serverNames` |

**Удали прежний сторонний SNI из карточки Host.** Явно заданный SNI
переопределяет унаследованное значение. Вместо явного нового SNI можно
оставить поле пустым, чтобы наследовать `serverNames` из выбранного inbound.
Сохрани карточку. Подробнее о наследовании — в
[документации Remnawave Hosts](https://docs.rw/learn-en/hosts/).

Здесь Hosts — раздел панели Remnawave. Файл `/etc/hosts` на VPS менять
не требуется. Поле HTTP `Host` в транспортных настройках также не нужно
заполнять только ради self-steal для обычного TCP/REALITY.

Для XHTTP Host выбери **XHTTP inbound** и его публичный порт, например
`8443`. В Address и SNI укажи домен сертификата nginx. Поле транспорта
`Host` можно оставить пустым, если клиент берёт то же имя из SNI; если оно
уже явно заполнено тем же доменом и соединение работает, менять его не нужно.
`Fingerprint: firefox` — настройка клиента, не nginx. `ALPN: h2,http/1.1`
совместим с локальным HTTP/2-сайтом. Для TCP inbound создай отдельную карточку
Host с тем же Address/SNI и его публичным портом, например `443`.

В итоге адрес подключения ведёт на VPS, порт — на публичный REALITY inbound,
а SNI совпадает с доменом self-steal. В Address нельзя указывать
`127.0.0.1`, а в Port — локальный `9443`.

### 9. Создай группу доступа — Internal Squad

В панели открой **Internal Squads**, создай группу, например `My VPN`,
или отредактируй существующую. Включи в ней **тот же inbound**
`Self-Steal → VLESS_SELFSTEAL`, который выбран в Host и на ноде, и сохрани.
Для двух карточек Host включи в Internal Squad оба соответствующих inbound,
если пользователь должен видеть оба подключения.
Подробности — в [документации групп доступа](https://docs.rw/learn-en/squads/).

Если профиль копировался, inbound из копии нужно добавить в группу отдельно:
привязка прежнего inbound не даёт доступа к новому. External Squads для
базовой схемы не требуются.

### 10. Создай пользователя и получи ссылку подписки

В панели открой **Users → Create user**. Задай имя, будущую дату окончания
доступа и подходящий лимит трафика. В **Access Settings** назначь созданную
Internal Squad `My VPN`. Сохрани пользователя и убедись, что он активен,
срок доступа не истёк и лимит не исчерпан.

В карточке пользователя скопируй **ссылку подписки** через значок ссылки
или соответствующее поле. Это персональная ссылка, а не адрес входа в панель
и не `https://node.example.com`. Панель должна выдавать публично доступный
адрес подписки. Настройка пользователя и получение ссылки описаны в
[официальной инструкции Users](https://docs.rw/learn-en/users/).

Если пользователь уже есть, достаточно проверить его группу и актуальность
доступа. Ссылку подписки считай данными доступа и не публикуй.

### 11. Импортируй подписку и подключи клиент

На телефоне или компьютере установи клиент с поддержкой VLESS/REALITY.
В нём выбери добавление по ссылке подписки, вставь ссылку пользователя из
предыдущего шага и загрузи список подключений. Для первого подключения
выбери Host `Мой VPN`. При запросе системного разрешения на VPN предоставь его.

Обнови подписку в клиентском приложении. Если используешь отдельно
импортированную ссылку, импортируй её актуальную версию. Проверь, что
в выбранном подключении указан новый SNI и правильный публичный порт.
Подключись к ноде и открой сайт через VPN.

Для обычной проверки сайта через публичный порт REALITY можно выполнить
с другого компьютера, подставив свой домен и порт:

```bash
curl -I --http2 https://node.example.com:8443/
```

В Windows PowerShell используй `curl.exe` вместо `curl`. Если установленная
сборка curl не поддерживает HTTP/2, выполни команду с другого компьютера
с поддерживающим HTTP/2 curl. Этот запрос
проверяет HTTPS-маскировку через публичный порт, но не авторизацию
VPN-клиента. Успешное подключение клиента проверяй отдельно.

### 12. Убедись, что настройка завершена

- Нода доступна панели, Xray запущен с нужным Config Profile и inbound.
- `bash check.sh` на VPS выводит `SELF-STEAL READY`.
- В Host выбран тот же inbound, Address ведёт на VPS ноды, Port равен
  публичному порту профиля, SNI совпадает с доменом сертификата.
- Пользователь активен и входит в Internal Squad с этим inbound.
- Подписка содержит Host; клиент подключается и открывает сайты через VPN.

При желании отдельно проверь повторный запуск установки:

На VPS из папки проекта:

```bash
bash install.sh --install 2>&1 | tee install-repeat.log
bash check.sh
```

Установщик должен повторно использовать подходящий сертификат и свои
файлы. При ошибке сохрани лог текущего этапа. Не запускай `uninstall.sh`
для диагностики: он удалит сайт и локальный TLS-сервер, на который
уже может быть направлен REALITY target.

## Если на одном из шагов возникла ошибка

| Симптом | С чего начать |
| --- | --- |
| Нода недоступна панели | IP ноды, совпадение API-порта с `NODE_PORT`, секреты из Compose и доступ от IP панели |
| DNS не проходит проверку | A-запись на IP ноды, отсутствие AAAA для этого имени, режим DNS only и завершение обновления DNS |
| Сертификат не выпускается | Доступность TCP/80 снаружи и правильный DNS; не повторяй выпуск многократно без устранения причины |
| После назначения профиля Xray не запускается | Ошибки JSON, незаменённые маркеры ключей, занятый публичный порт и журнал Node |
| В подписке нет Host | Видимость Host, выбранный inbound, Internal Squad пользователя, срок и лимит доступа |
| Подписка вообще не загружается | Доступность адреса подписки панели с устройства; это отдельный адрес от домена self-steal |
| Host есть, но VPN не подключается | Публичный порт, SNI, актуальность подписки и работа локального nginx |

Журнал Node смотри на VPS из его каталога Compose, например:

```bash
cd /opt/remnanode
docker compose logs --tail=100
```

Названия разделов интерфейса могут различаться между версиями панели.
Во всех привязках ориентируйся на один выбранный профиль и один inbound.

## Что устанавливается и расходует ресурсы

| Компонент | Для чего нужен | Работа в фоне |
| --- | --- | --- |
| `nginx` | HTTP-сайт и локальный TLS-сервер для REALITY | Постоянная служба |
| `certbot` и его зависимости Python | Выпуск и продление сертификата | Запускается по расписанию `certbot.timer` |
| `openssl` | Работа с сертификатами и ключами | Только при вызове |
| `ca-certificates` | Доверенные центры сертификации | Отдельной службы нет |
| `git` | Получение и обновление файлов проекта | Только при вызове |
| `curl`, `iproute2` | HTTP/TLS-запросы и просмотр слушающих портов через `ss` | Только при вызове |
| `python3-configobj` | Чтение настроек продления Certbot | Только при вызове |

Установщик добавляет только отсутствующие пакеты `nginx`, `certbot`, `openssl`
и `ca-certificates` вместе с обязательными зависимостями Ubuntu.
Утилиты из шага 3 нужны для клонирования и предварительных проверок.
`python3-configobj` также входит в зависимости Certbot; отдельная установка
на шаге 3 позволяет выполнить проверки вспомогательных функций до установки Certbot.
Необязательные рекомендуемые пакеты отключены параметром `--no-install-recommends`
в обеих командах установки. Уже установленные пакеты этот параметр не удаляет.

Проект не добавляет контейнеры, базу данных или постоянно работающий скрипт.
Нагрузка nginx зависит от числа соединений и TLS-запросов; журналы занимают место
на диске. Фиксированных обещаний по RAM и CPU нет: замеры на VPS не выполнялись.
Настройки процессов nginx используются из пакета Ubuntu; проект не добавляет
собственных заданий ротации журналов.
Стандартный сайт nginx сохраняется и может отвечать на запросы к IP или другим
именам; сайт self-steal выбирается по настроенному домену.

## Как работает установщик

`bash install.sh --check` выполняет предварительную проверку без изменения
конфигурации. `bash install.sh --install` устанавливает пакеты, создаёт свои
файлы, включает автозапуск nginx и `certbot.timer`, запускает или перечитывает
конфигурацию nginx. При первом выпуске сертификата запрашивается email.
Certbot использует режим `webroot` и сам не переписывает конфигурацию nginx.

| Путь | Содержимое |
| --- | --- |
| `/etc/remnawave-selfsteal/state.conf` | Домен, локальный порт и версия формата состояния |
| `/etc/remnawave-selfsteal/packages.started` | Отметка о начале установки пакетов |
| `/etc/remnawave-selfsteal/renewal.checked` | Запись об успешном пробном продлении и отдельной проверке применения сертификата |
| `/etc/remnawave-selfsteal/tls-v0.1.0.conf.bak` | Исходный TLS-конфиг, если выполнялся переход со старой версии |
| `/etc/nginx/sites-available/remnawave-selfsteal.conf` | HTTP-сайт на TCP/80 |
| `/etc/nginx/sites-available/remnawave-selfsteal-tls.conf` | TLS-сервер на `127.0.0.1:9443` |
| `/etc/nginx/sites-enabled/` | Ссылки на два конфига проекта |
| `/var/www/remnawave-selfsteal/` | Страница сайта и файлы подтверждения HTTP-01 |
| `/etc/letsencrypt/live/ТВОЙ_ДОМЕН/` | Ссылки Certbot на действующий сертификат и ключ |
| `/etc/letsencrypt/renewal/ТВОЙ_ДОМЕН.conf` | Настройки продления сертификата |
| `/etc/letsencrypt/renewal-hooks/deploy/remnawave-selfsteal-nginx.sh` | Скрипт проверки и перечитывания конфигурации nginx после продления |

Повторный запуск использует сохранённый домен и подходящий действующий сертификат.
Изменённые вручную файлы не перезаписываются. Исключение — точно распознанный
старый шаблон TLS-конфига: его обновление описано ниже. Если операция с пакетами
прервалась и `dpkg` сообщает о незавершённой настройке, сначала восстанови
состояние пакетного менеджера согласно его сообщению, затем повтори установку.

После запуска или перечитывания конфигурации nginx выполняются повторные запросы
готовности с порогом ожидания 30 секунд; выполняющийся запрос и завершающий
диагностический запрос могут увеличить общее время. Проверяется работа HTTP-01,
а затем TLS 1.3 с согласованным HTTP/2.

Одновременные установка и удаление блокируются общей блокировкой.
Оставшиеся после прерывания временные записи состояния очищаются только внутри
каталога root с правами `700`, при совпадении ожидаемых имени, типа, владельца
и прав файла. Неожиданные файлы и символические ссылки останавливают операцию.

`check.sh` проверяет DNS, nginx, HTTP, сертификат, локальные TLS 1.3/HTTP/2,
таймер продления, скрипт применения сертификата и сохранённую запись пробного
продления. Он не запускает новое продление и не проверяет авторизацию VPN-клиента.
Для чтения настроек Certbot учитывается привязка домена в `webroot_map`.

Запись успешного продления содержит хеши настроек Certbot и скрипта применения
сертификата. При их изменении или старом формате записи следующий `--install`
повторит пробное продление. Поскольку Certbot не передаёт ошибку deploy hook
через свой код завершения, установщик затем отдельно запускает установленный
скрипт с доменом и путём сертификата, требует успешного завершения и повторно
проверяет TLS-сервер. Только после этого создаётся запись об успехе.
При ошибке установка остаётся незавершённой; после устранения причины повтори
`--install`. Это проверка текущего состояния, а не гарантия всех будущих продлений.

## Обновление установленной версии

Выполняй обновление из root-сессии на VPS. Сохрани собственные изменения
репозитория до `git pull`; не удаляй каталог состояния или сертификаты.

```bash
cd /opt/remnawave-selfsteal
git pull --ff-only
set -o pipefail
bash install.sh --install 2>&1 | tee install-update.log
bash check.sh
```

Старый неизменённый TLS-шаблон из коммита `2f225ce` (без HTTP/2) распознаётся
автоматически. Установщик сохраняет его в
`/etc/remnawave-selfsteal/tls-v0.1.0.conf.bak`, атомарно заменяет новым шаблоном
и запускает `nginx -t`. При ошибке этой проверки восстанавливается прежний файл.
Если шаблон или права старого файла отличаются от ожидаемых, автоматический
переход прекращается. Не удаляй такой файл вслепую: сначала разберись с отличиями.

При ошибке перечитывания конфигурации резервная копия остаётся на месте.
При необходимости возврата к старой версии восстанови её в
`/etc/nginx/sites-available/remnawave-selfsteal-tls.conf` с правами `644`,
проверь `nginx -t` и только затем перечитай конфигурацию. Старый шаблон не имеет
HTTP/2 и не пройдёт текущую проверку готовности; это временный откат.
Актуальный `uninstall.sh` распознаёт оба исходных шаблона.

Для прежней записи успешного продления будет выполнено новое пробное продление
с отдельной проверкой применения сертификата. Домен, ключи REALITY, публичный
порт и настройки панели при обновлении скрипт не меняет.

## Обслуживание и журналы

Для продления сохраняй A-запись на VPS и доступность TCP/80 снаружи.
Certbot запускается системным таймером; дополнительно добавлять его в cron
или постоянно запускать установщик не требуется.

Для просмотра состояния на VPS:

```bash
systemctl status nginx certbot.timer --no-pager
systemctl list-timers --all certbot.timer
journalctl -u nginx -u certbot.service --since '24 hours ago' --no-pager
```

Журналы nginx по умолчанию находятся в `/var/log/nginx/access.log`
и `/var/log/nginx/error.log`, журнал Certbot — в
`/var/log/letsencrypt/letsencrypt.log`. Настройки можно найти в
`/etc/nginx/nginx.conf`, `/etc/logrotate.d/nginx` и `/etc/logrotate.d/certbot`;
доступность файлов ротации зависит от установленного пакета и конфигурации VPS.
Следи за свободным местом и ошибками продления, особенно после изменения DNS,
сетевого экрана или конфигурации nginx. Файлы `install*.log` и `check.log`,
созданные командами из этой инструкции, системной ротацией не обслуживаются.

Для повторной ручной проверки продления укажи свой домен:

```bash
certbot renew --dry-run --run-deploy-hooks --cert-name node.example.com
```

Успешный код завершения одной этой команды не подтверждает успешность deploy hook:
просматривай сообщения об ошибках и журналы. Эта ручная команда не создаёт
`renewal.checked`. Чтобы повторить полный этап установщика после изменения
настроек продления, используй `bash install.sh --install`.
Если настройки не менялись и запись актуальна, установщик пропустит новое
пробное продление.

## Удаление

1. Сначала верни рабочие `target`/`dest`, `serverNames` и при необходимости `xver`
   в профиле Remnawave, восстанови SNI в Hosts. Если возвращаешь другой профиль,
   восстанови привязки ноды, Host и доступ пользователей в Internal Squads.
2. Примени настройки, обнови подписку клиента и убедись, что подключение
   больше не зависит от `127.0.0.1:9443`.
3. На VPS из root-сессии выполни:

```bash
cd /opt/remnawave-selfsteal
bash uninstall.sh
```

Скрипт удаляет только распознанные файлы проекта, включая свою резервную копию
старого TLS-конфига. Изменённые вручную файлы и символические ссылки в родительских
каталогах останавливают удаление. Сертификат Let's Encrypt удаляется только
после отдельного согласия. Если оставить его, для будущего продления потребуется
другой работающий HTTP-01 сайт с нужным каталогом; прежний сайт уже удалён.

**Пакеты nginx и Certbot, их службы и автозапуск сохраняются.** Стандартный сайт
nginx может продолжать слушать TCP/80, а `certbot.timer` — запускать продление.
Это позволяет сохранить другие сайты и сертификаты, добавленные на VPS позже.

Только если nginx больше не обслуживает другие сайты, а Certbot не продлевает
другие нужные сертификаты, можно убрать оставшуюся фоновую работу:

```bash
systemctl disable --now nginx certbot.timer
```

Остановка таймера не прерывает уже запущенное продление: дождись завершения
`certbot.service`. Отключение служб не удаляет пакеты и не закрывает правила
сетевого экрана. Правила SSH, API Node и действующего REALITY-порта сохраняй.

Повторная установка с нуля после удаления всё ещё ограничена запретом на
существующий nginx и сертификат выбранного домена. Для штатного обновления
используй раздел обновления выше. Не выполняй массовое удаление пакетов или
`/etc/letsencrypt` ради обхода ограничений: там могут находиться чужие настройки.

## Статус версии

Изменения внесены без запуска тестов и контейнеров по просьбе владельца проекта.
Выпуск и продление настоящего сертификата, работа systemd, переход со старой
версии и подключение через Remnawave ещё требуют проверки на тестовой VPS.

Тег `v0.1.0` планируется после проверки чистой установки Ubuntu 24.04,
повторного запуска, восстановления после прерывания и удаления.
До этого ветка `main` остаётся версией в разработке.
